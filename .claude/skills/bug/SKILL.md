Run `node .claude/hooks/lib/mdd-ensure.cjs` first, before anything else. It creates `.mdd` and its essential files if missing, and is a silent no-op otherwise.

Fix the bug: $symptom

Do NOT create a new feature doc. A bug belongs to an existing feature, the job is to
find which one, record the bug, fix it, and mark it done. Never work on main.

## B0, parse
If `$symptom` is empty, ask what is broken and where it should work correctly.

## B1, triage (find the owning doc)
Read the frontmatter ONLY (not bodies) of every `.mdd/docs/*.md` except archive: `id`,
`title`, `tags`, `source_files`. Score each doc against the symptom: tokenize the
symptom into significant words (drop stopwords and bug-words like fix/broken/error), and
for each word add +2 if it is in the doc's `tags`, +1.5 if in the `title`, +1 if in a
`source_files` filename. A doc scoring 2.0 or higher is a candidate. Sort descending. If
nothing scores 2.0, stop and show the full doc list with guidance (the code may be
undocumented, run `/reverse-engineer`, or the symptom uses different words than the
tags). Do not proceed without at least one candidate.

## B2, confirm
Present the candidates with their scores and what matched, plus the full doc list so the
user can add a low-scoring one. Ask (multiSelect) which docs the bug relates to, require
at least one. This is the related-docs set.

## B3, document the bug
For each related doc, read it, compute the next bug id (highest existing `B<N>` in its
`## Bugs` table plus one, or B1), and add a row `| B<N> | <symptom> | Open | - | <today> | - |`.
If the doc has a `## Bugs` section, append; if not, create one (after `## Known Issues`
or the last section, never before Purpose/Architecture/Business Rules/Data Model) with
the header row `| ID | Description | Status | Fixed In | Reported | Fixed |`. A bug
spanning multiple docs gets its own row and B-id in each. Report the ids added.

## B4, fix
Ask how to proceed:
- Lightweight: read the related docs' `source_files`, grep `src/` to locate the symptom's symbols, then use LSP `goToDefinition`/`findReferences` to pin the real definition and every call site (grep alone over- and under-matches), read the candidates, then diagnose before touching anything (what the code does, why it causes the bug, the fix, the side-effect risk), make the minimal targeted change (no adjacent refactor), and verify with typecheck plus the test runner or a real run.
- Full MDD: run build Phases 4 to 7 for the fix, treating the related docs as the documentation (skip Phases 1 to 3). Write a failing regression test first (Red Gate), fix to green, verify. Test Freeze applies once phase is implement.

## B5, mark complete
After the fix verifies, update each related doc's bug row: Status `Open` -> `Completed`,
`Fixed In` = `<file>:<line>` of the root-cause fix (or `see <other-id>:B<N>` when the fix
lived in another feature), and the Fixed date. (The connections map is regenerated by the
connections-sync hook when the doc is written, no manual rebuild needed.) Report the bug,
the fix location, the docs updated, and the branch,
then offer to commit and merge (stage, conventional commit, merge --no-ff, ask before
push).

## Messaging

Print one plain `[bug] <what is happening>` line when starting (and at each later
stage of this flow), then work silently. Any question to the user is a
`WAITING ON YOU` block with numbered options, never an open-ended stop. End with a
short DONE line: what was produced, the key numbers, and the natural next action
(or `BLOCKED, <reason>` with numbered options).
Mirror the steps to the status bar: run `node .claude/hooks/lib/statusbar.cjs set bug <step> <total> "<label>"` alongside each line and `node .claude/hooks/lib/statusbar.cjs done bug` with the DONE line (pre-approved, best-effort, silent).
